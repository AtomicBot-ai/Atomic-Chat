# 2026-10-16 — Ask before every MCP and third-party tool call

- **Context:** MCP tools ran without asking in both engines. Chat's `allowAllMCPPermissions` defaulted to on, and a v1 store migration forced it on for every existing user. That default came from upstream; nobody here chose it. The agent took the same value as `auto_approve_mcp` (serde default `true`), and it also classed any MCP tool whose server sent `readOnlyHint` as `ResourceClass::McpRead`, which skipped the approval gate even with the switch off. The hint is the server's own claim about itself, so a malicious or buggy server could get a write past the user by marking it read-only. The owner asked that MCP and plugin tools ask for approval.
- **Decision:** Every MCP tool call asks by default, in Agent mode and in regular chat. The only ways around the prompt are choices the user makes deliberately: "Always allow" on one exact action (the existing fingerprints in the agent, the per-thread tool list in chat), the composer's per-thread "skip" mode, or the global "Auto-approve MCP tool calls (not recommended)" switch in Settings → General and Connectors, which now carries warning text. In the agent, every MCP tool the bridge resolves is `ApprovalGated`. `McpRead` is gone, and `readOnlyHint` now only adds a `[read-only]` marker to the prompt. `resource_class::mcp_opt_in_waives_approval` is the one place the opt-in applies, and it only covers `mcp.*` names. `AgentTurnRequest.auto_approve_mcp` defaults to `false`. On the frontend, `allowAllMCPPermissions` defaults to `false`, and store version 2 (`migrateToolApprovalState`) sets it back to `false` once for existing users, keeping their per-tool approvals. A user who turns it back on afterwards keeps that choice. Chat's gate lives in `approveChatToolCall` (`lib/mcp-approval.ts`).
  The plugin and extension surfaces were checked one by one. MCP servers are the only third-party code the model can call; they are now gated. Skill `skill.run_script` runs scripts that come with installed skills. It was already `ApprovalGated` and is not affected by the MCP opt-in (pinned by test). The Tauri plugins and `extensions/*` are first-party and ship inside the app bundle, with no third-party install path. The only model-facing pieces are the RAG `docs.*` and chat RAG tools, which read the user's own document index, so they are not applicable. Launch-page integrations start external coding agents when the user clicks, and the model cannot invoke them, so they are not applicable either.
- **Consequences:** Users who relied on the old silent default will see approval prompts for MCP tools again, once per tool per thread if they use "Always allow" in chat, or once per exact action in the agent. MCP calls no longer batch, because a gated call runs solo, even when the opt-in is on. Turning the opt-in on still never covers built-in shell, file, network-fix or skill-script actions. If a future surface lets third-party code act on the user's behalf, it should come in as `ApprovalGated` and not get its own bypass.
