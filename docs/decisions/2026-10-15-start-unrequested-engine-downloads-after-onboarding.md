# 2026-10-15 — Start unrequested engine downloads after onboarding, and show downloads as a plain list

- **Context:** Both llama.cpp extensions started engine downloads from `onLoad`: a move to a newer release tag of the build in use (`reconcileBackendReleaseTag`), and for TurboQuant the first-run adoption of the hardware-optimal build. On the owner's fresh install (2026-10-14 `app.log`) that fetched 17.6 MB and 13.7 MB of CPU builds within 11 s of launch, before onboarding had asked anything. One of them was for TurboQuant, which ships switched off on fresh installs (2026-08-19). The download drawer opened by itself on the first download, so these popped over the onboarding screen. The drawer drew a Tetris-style falling-blocks canvas (PR #119) whose animation loop ran every frame while anything downloaded, drawer open or not. The owner found it looked bad and asked for it to be removed and rethought. Separately, `decompress` was a synchronous Tauri command, so it ran on the main thread and froze the window while an archive unpacked. And a download whose CDN stopped sending mid-transfer waited forever, because reqwest 0.11 has no read timeout.
- **Decision:** `onLoad` only resolves a parked `latest/<variant>` sentinel (upstream, `allowUpgrade: false`). Release-tag moves and TurboQuant's first-run adoption wait for a new `runDeferredBackendMaintenance()` on each extension. `StartupBackendCoordinator` calls it once per process, 15 s after onboarding is done, after the startup tier upgrade if that has begun, and only for providers that are switched on (`runDeferredBackendMaintenance` in `lib/startupBackendRecommendations.ts`). The drawer is a plain list of `DownloadProgressRow`s (name, thin bar, size, speed, time left, Pause/Cancel). Engine builds the app fetches by itself sit below it as single lines (`isEngineDownload`: task ids starting `llamacpp`). The drawer never opens by itself: a download the user started gets a toast with a "View" button, and engine builds get none. `decompress` is an async command that does the work on a blocking thread. A transfer that receives no bytes for 60 s is treated as a stream error and resumed with a Range request. Bundled agent skills are copied only when the app version changed, the data folder has never been seeded, or `IS_CLEAN` is set; copying them on every launch held the window back for seconds before it appeared.
- **Consequences:** A fresh install no longer downloads anything before the user has chosen something, and never downloads for a provider that is off. A returning user's release-tag update arrives about 15 s after launch instead of immediately. Nothing animates in the drawer. A new bundled skill only appears after an app-version change, which is when the bundle changes anyway.
