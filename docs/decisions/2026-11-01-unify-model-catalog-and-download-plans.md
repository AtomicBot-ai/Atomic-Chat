# 2026-11-01 — Use one model catalog and persist immutable download plans

- **Context:** Independent desktop catalogs duplicate sources and allow metadata from one HF tree to describe bytes from another. Resuming against a refreshed catalog can mix model shards, projectors or configurations from different versions. A repository commit identifies the tree; a file SHA-256 identifies its contents.
- **Decision:** `atomic-chat-conf/models/catalog.json` is the editable source for managed models and recommendations. Generated Hub discovery continues to use `atomic-chat-model-catalog`, its index and bundled fallback; see the 2026-11-02 preservation decision. Entries have stable IDs, formats and variant IDs; collections reference them. The generator retains historical envelopes and omits only fields old exports never exposed. Validation compares all ten exports offline. The migration preserves versions, IDs, sizes and hashes, including the pinned PrismML families. Engine runtime descriptors and mobile catalogs retain their existing contracts.
- **Download contract:** Resolve a version, read its metadata, check compatibility and space, persist a version-1 plan, then transfer. Every HF file records repository, full commit, path, destination, byte count, available hash and purpose. Sources in different repositories have independent revisions. GGUF shards and projectors are separate items; MLX records its selected tree and checks the total weight, configuration and tokenizer bytes before persisting a new request. Voice/draft sources come from conf; engine/model matching remains in code. Metadata uses the app's existing proxy transport.
- **Persistence:** Desktop shares the whole catalog through `atomic_unified_model_catalog_v1`. Plans use `atomic_model_download_plan_v1:<task-id>`. GGUF, MLX and diffusion also retain their original request so upper layers cannot reselect files on Resume. Plans contain no tokens or proxy credentials. Resume reads these snapshots before contacting HF and ignores catalog updates. Old unfinished requests without a commit are refused; partial files and old caches remain. Installed models are not automatically replaced.
- **Catalog correction (2026-11-02):** Live validation confirmed Kimi K2.6 DFlash commit `3401c5c9bbd1e1989529bc36a334fa3d3d39691d` contains `config.json` and one `model.safetensors`, rather than the index and three shards inherited from the static registry. Correct the catalog selector and regenerate all bundled snapshots without changing the commit or legacy exports. The explicit updater now refuses missing required files before saving; regression tests prepare the real pinned layout without fetching the large weights.
- **Installed and optional models:** Diffusion installation receipts retain the family contract used for existing bytes. Optional voice sources are resolved when a download is requested, so a catalog without voice cannot prevent application startup. Voice Resume reads its saved plan before looking up a current source. Bundled byte counts remain a display fallback for historical installed-model records.
- **Integrity:** Missing/mismatched commits or metadata fail before transfer and registration. An unavailable declared commit never falls back to main. Files with SHA-256 are checked before reuse; HF files without a content hash are fetched again rather than identified by size alone. Core keeps an array-returning GGUF metadata API with additive `revision` support; clients still own transfers and HTTP contracts are unchanged.
- **Alternatives:** A second manually edited sources file leaves competing sources of truth. Replacing legacy formats breaks released readers. Resolving main again during Resume loses the identity of partial bytes. Runtime history searches are expensive and ambiguous; history was used only to identify existing bytes during migration.
- **Consequences:** Whole-document caches and bundled snapshots support offline fallback. New downloads require HF metadata. Plan storage must succeed before transfer; exhausted storage safely refuses a request. Snapshots remain available for recovery and provenance. Remove old exports only after explicitly ending support for their consumers. Publish compatible conf data, release core, then pin its exact released version in both clients before their releases.
