# 2026-09-21 — Run desktop e2e scenarios side by side

- **Context:** Every desktop e2e scenario already had a root of its own (`ATOMIC_E2E_DATA_ROOT`: data folder, settings, stand-in home, webview store, core, ports), yet the suite ran one app at a time, about 275 s for 39 scenarios. Four things outside the data folder were shared. The single-instance socket is named after the app identifier alone (`/tmp/<identifier>_si.sock`), so a second e2e app handed over to the first and exited with code 0. The harness stopped "the app" by killing every process of the binary. It swept stale profiles before every session, by "no process names this root" — which is what a neighbour's profile looks like while it is being prepared. And the MLX and Foundation Models scenarios swapped servers inside the build's `resources/bin`.
- **Decision:** In an e2e build the app identifier gets a tag derived from the root (`run_identifier`), set on the context before the app is built; the single-instance plugin stays, and two apps on the same root still meet. Rejected: leaving the plugin out of e2e builds, which would take that behaviour out of the build under test. Windows of parallel runs are cascaded by `ATOMIC_E2E_WINDOW_SLOT` (the vitest worker's id), since each is kept on top and a window covered completely gets no animation frames. The core's sidecar folder comes from `<root>/sidecars` when the run has one. In the harness: the app is stopped by the pids listening on its session's WebDriver port (a self-restarted app keeps the port); stale profiles are swept once per run in `globalSetup`; a run's socket is removed with its profile. `E2E_WORKERS` (default 4; 1 is the old one-at-a-time run) sets how many scenario files run together; scenarios within a file still run in order. Not made a production option: an environment variable that moves the app's profile would let any process that can set it hand the user another profile.
- **Consequences:** Measured on a 16-core M-series machine, all green: 1 worker 277 s, 4 workers 76 s, 6 workers 56 s — bounded by the longest file (the data-folder scenarios, about a minute). Keyboard input does not cross windows: the embedded driver delivers it to its own webview. The Hub fixture's port stays baked into the build, which is fine while one file uses it. Parallel is the default, by the user's choice on the day it was built; `E2E_WORKERS=1` is the way to tell a real failure from one that only load produces. Time-bounded assertions ("a core within fifteen seconds") are the ones to watch under load. Nothing the tests do is left outside a profile any more.
