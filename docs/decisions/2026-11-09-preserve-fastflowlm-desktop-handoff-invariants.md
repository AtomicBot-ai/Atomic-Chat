# 2026-11-09 — Preserve FastFlowLM desktop handoff invariants

- **Context:** The CLI desktop handoff exposed six gaps in the initial desktop adapter: settings waited for model readiness, invalidation dropped a running scan's guard, developer catalogs shared production cache state, onboarding mixed engines, Linux authorization required polkit, and gated models had no actionable terms links.
- **Settings and discovery:** Provider discovery publishes settings independently through an optional callback. Startup refreshes provider visibility concurrently, preserves cached models during settings publication, and rereads settings after discovery so a slow scan cannot undo an edit. The FLM extension retains one scan promise: mutations advance a revision, wait for the old scan, and repeat until its result reflects the latest mutation. Even callers waiting before the mutation receive the fresh result. Overlapping provider discoveries return the newest discovery, so a response delayed by another engine cannot overwrite a later FLM refresh.
- **Catalog source identity:** Keep accepted catalogs, pending fetches, status and persistent cache separate for each exact source URL. Configure the app's source once so synchronous planners use the same snapshot as the catalog screen. Reject legacy cache documents without a source identity: earlier developer overrides could write into the production key. This costs one metadata refetch; offline startup uses the bundled complete baseline rather than an ambiguously sourced document. Valid source-bound cached documents remain authoritative, including an empty FLM collection.
- **Onboarding:** Scope rows to an explicitly selected bare provider ID. Persist the engine and one selected row per engine in the existing onboarding store. Offer all FLM variants, placing the editorial recommendations first in their own section; do not apply GPU fit estimates to FLM. Represent installed variants through their existing library row rather than offering a duplicate download. Keep a missing saved variant unselected until the user chooses again. The existing core check runs before a new FLM download; installing an engine never switches the selected provider.
- **Linux authorization:** Prefer an installed `xdg-terminal-exec` with `sudo`, then polkit; provide the exact guarded terminal command when automatic prompting is unavailable. Password input belongs to the system terminal. An unprivileged fixed shell wrapper invokes only the trusted copied core CLI with the separately supplied request SHA-256. A private atomic launch guard prevents repeats; a bound failure receipt covers sudo refusal without overwriting a real helper receipt. Journal recovery reads the same receipt or displays the same guidance, never automatically launches another helper. A late native reply cannot replace a newer core snapshot. No new executable, path or command is accepted from webview IPC.
- **Gated models:** Show terms links from the selected variant's Hugging Face sources and a link to the existing token settings even when a token is already saved. A token does not prove that model terms have been accepted. An omitted source host means Hugging Face, as in the SDK contract.
- **Alternatives:** Clearing a running scan allows concurrent scans and stale store writes. One catalog cache cannot establish which source authorized a file plan. A mixed onboarding list can install a model for a different engine. Collecting passwords in React or replaying an unknown helper would weaken the existing authorization boundary.
- **Validation limits:** Focused TypeScript/Rust fixtures, compilation and Chromium geometry checks cover these transitions. They do not qualify real Linux terminal/polkit behavior, Windows UAC, NPU inference, reboot recovery or API restart with a live engine. Those checks remain open; aggregate verification requires separate approval.
