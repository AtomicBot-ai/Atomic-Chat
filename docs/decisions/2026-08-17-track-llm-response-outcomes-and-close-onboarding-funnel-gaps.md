# 2026-08-17 — Track LLM response outcomes (`chat_response_received`) and close the onboarding funnel's blind spots

- **Context:** Telemetry recorded that a message was *sent* (`chat_request_sent`, six properties) and nothing about what came back. There was no success rate, no latency, no throughput, no failure taxonomy — a turn that errored, was cancelled, or died on a context overflow looked identical to one that answered perfectly. Nearly all the numbers already existed and were being thrown away: `custom-chat-transport.ts` computes `finishReason`, `usage`, `activityDurationMs`, `tokenSpeed` and speculative-decoding counters purely for the UI indicator; `ttft-timing.ts` has a full α→θ stage breakdown (client → proxy → engine, with markers emitted from `proxy.rs`) behind an `import.meta.env.DEV` gate that printed a `console.table` and shipped nothing; and the transport's `onTokenUsage` callback was plumbed end-to-end with no subscriber. Three send paths (`regenerate`, `edit`, and the AI SDK's `onError`) emitted no event at all, so even the send count was short. On the onboarding side, the flow's middle was instrumented but both ends were dark: completion could only be *inferred* from a later `model_load`, three of the four exit paths were silent, and an auto-start suppressed `setup_screen_shown` entirely, dropping those sessions out of the funnel.

- **Decision:** Add `chat_response_received` — exactly one event per assistant turn, carrying outcome (`success | error | aborted | truncated_continued | truncated_stopped`), a `ChatFailureKind` taxonomy, TTFT/latency/TPS, token and speculative-decoding counts, context fill, attachment shape, and tool usage — correlated to its `chat_request_sent` by a shared `turn_id`. Promote TTFT marker collection out of the dev gate (the `console.table` stays gated) and attach the stage breakdown to the event. Enrich `chat_request_sent` and add the three missing send paths. For onboarding, add `onboarding_completed` (with `exit_path` and `duration_ms`) on the `hasNavigatedRef` choke point, `backend_step_shown`, `setup_local_model_run`, `onboarding_model_reminder`, `provider_key_configured`, a `rendered` flag on `setup_screen_shown`, and `is_first_launch` on `app_opened`.

  Three PII rules were chosen deliberately and are enforced by tests: **text length is reported only as a bucket** (`lt_100`, `100_500`, …), never a count; **attachment filenames never leave the device** — only an extension that is on the app's own accept-list, everything else collapsing to `'other'`; and **tool names from user-configured MCP servers are hashed** to `mcp_<fnv1a8>` (a server name can itself describe the user's internal systems) while shipped tools stay readable. Token counts from `usage` are reported exactly — they are an engine metric, not the shape of the content.

  All property-shaping lives in `lib/chat-telemetry.ts` and `lib/onboarding-telemetry.ts` rather than at the call sites. This is a hard constraint, not a preference: `custom-chat-transport.ts`, `SetupScreen.tsx` and `SetupBackendStep.tsx` are all under `tests/coverage-floor.json`, and the backend step's **branch floor is 100 %** — so its call site had to be a single argument-free call, and the helper does its own defaulting.

- **Consequences:** The funnel `chat_request_sent → chat_response_received` is now closed, and TTFT can be attributed to client, proxy or engine on real user hardware. `rate_limit` (429) and `content_filter` are classified even though the client still has no handling for either — the gap becomes measurable before it is fixed. Watch for: (1) a turn with tool calls emits on its terminal step, so `tool_call_count` reflects the final assistant message rather than the whole turn; (2) a context-limit continuation deliberately closes one turn and opens another, so one user send can produce two response events — `truncated_continued` marks the first; (3) `setup_local_model_run` is a **new** event rather than an extra `trigger` on `setup_local_model_autostarted`, so existing dashboards keep their meaning; (4) failures are throttled per `(model, error_kind)` on a 5-minute window, mirroring `shouldEmitModelLoadFailure`, so a retry-looping backend cannot dominate event-weighted metrics — failure *rates* are therefore under-counted by design.

  Not done: no `launch_id` super-property. Funnels must be built per `distinct_id` over a time window, which merges steps from multiple launches on the same day; `is_first_launch` covers the first-session case that matters most.
